## F-1 — non-blocking
Claim: E4's exception is conditioned on a remote operation "whose refs report success", and an operation that reports no refs at all — the up-to-date or no-op fetch — does not meet that condition, so the credential-helper noise this region exists to neutralise still falls under the trigger it sits next to.
Location: `skills/directive-invariants.md:154-155`, against `:110-114` and `:150-154`
Evidence: *Observed*, verified by reading and by running in this session. The `## Stop conditions` region now ends "...do not retry with different flags, and do not delete or create any ref to recover. A remote operation whose refs report success is not a failed command." (`:150`–`:155`). The exception's subject is qualified: it reaches an operation *whose refs report success*. The `## Base verification` region's widened sentence has the matching qualification — "Judge every remote operation — fetch, push, ls-remote — by the refs it reports, not by a credential helper's noise on stderr" (`:110`–`:114`). Neither sentence covers the case where there are no refs to judge by. That case is the common one, not the corner one, and it fired on this session's first command: `git fetch origin`, with stdout and stderr captured separately, exited `0`, wrote nothing to stdout, and wrote exactly one line to stderr — `fatal: failed to store: 100001` — with no `From …` line and no ref line at all. The same command scoped to a branch, `git fetch origin directive-authoring-consolidation`, exited `0` and printed the same `fatal:` line *plus* `From https://github.com/…` and ` * branch  directive-authoring-consolidation -> FETCH_HEAD`, which the exception does reach. So the two shapes of the same operation, seconds apart, fall on opposite sides of a condition whose whole purpose is that neither is a failure.
Consequence: An executor runs the base fetch, sees a line beginning `fatal:`, and looks for the rule that governs it. The Base verification sentence tells it to judge by the refs; there are no refs. The Stop conditions sentence tells it that an operation whose refs report success is not a failed command; this operation's refs reported nothing, so the sentence does not license it. What is left is "On any failed command … stop and report", and the executor stops before doing any work, reporting a failed fetch on a fetch that exited 0 and left the base correct. That is the same wasted-stop failure cycle 5's F-1 described, arriving now at the *start* of a session rather than the end, and it is worse there: nothing has landed, so the decision session receives a stop report it cannot distinguish from a genuinely moved base without re-running the fetch itself. Criterion 11: an underspecified condition, and an escalation trigger that fires on a state no rule in the file resolves. The reviewed ref's own directive had to state the rule at its top level in the widened form — "Judge every remote operation … by the refs it reports, not by credential-helper noise on stderr" — rather than rely on either region, which is the second cycle running in which a directive has had to hoist this sentence out of the file that is supposed to hold it.
Fix: Condition the exception on the exit status the operation actually reports rather than on refs it may not print — "A remote operation that exits successfully is not a failed command, whatever a credential helper writes to stderr" — which covers the no-ref fetch and the ref-reporting push with one sentence, keeps the exception where E4 correctly put it, and does not disturb the Base verification sentence, whose subject is which output to *believe* rather than whether a command failed. If the refs are to stay in it, the smaller alternative is one clause: "…whose refs report success, or which reports no refs and exits successfully, is not a failed command." Either is within the editing constraints that bind this file, since neither adds a section or a fence.
