## F1 — non-blocking
Claim: §8's implementation sentence cites the build-gating rule as the authority under which implementation may proceed without naming the condition that rule attaches, so the sentence reads as a permission where the rule it cites is a prohibition conditioned on Dave's per-task confirmation.
Location: specs/bin-land.md §8, lines 371-373; policies/document-metadata-policy.md lines 279-285.
Evidence: Inferred by reading, with both texts verified by running. §8 reads "Implementation — tests confirmed red, then code to green — may proceed under the build-gating rule in `policies/document-metadata-policy.md` without waiting on that document" (*observed*, read at this SHA). The cited rule reads "Do not build against a `draft` or `in-review` spec without explicit human confirmation. A task assignment referencing the spec establishes intent, but the agent must state the spec's current status and receive confirmation before proceeding. Confirmation is per-task, not per-session" (*observed*, `sed -n '279,285p' policies/document-metadata-policy.md`; the policy is `status: agreed`, so it governs). The rule's scope reaches this case: it "covers `specs/` documents (PRDs/TRDs) only" and defines building against as implementing code "whose requirements derive from that spec" (*observed*, lines 276-279), and `bin/land`'s implementation would derive from this PRD, whose frontmatter reads `status: draft` (*observed*, line 2). So the sentence is accurate about what the gate is not — the write-path document is not a precondition — and silent about what the gate is.
Consequence: An executor handed a directive to implement `bin/land` reads §8, finds implementation authorized "under the build-gating rule", and proceeds without stating the spec's draft status or obtaining the confirmation the rule requires — the precise omission the rule exists to prevent. The failure is quiet: the executor can cite §8 for having followed the governed document, and nothing in the spec contradicts it. The risk is highest for exactly the reader §8's sentence is written for, since a reader who opens the policy finds the condition immediately and one who takes §8 at face value never does.
Fix: Name the condition in the sentence — for instance, closing it with "which, while this spec's status is `draft`, requires Dave's explicit per-task confirmation before an executor builds against it". Proposed, not applied: the wording is the cycle-7 directive's and Dave's sequencing decision is what §8 records, so a reviewer amending it would be substituting its own text for dictated text. Dave's alternatives are to accept the addition, to leave the sentence as dictated on the ground that the policy governs whether or not the spec restates it, or to flip the spec to `agreed`, which retires the condition entirely.
