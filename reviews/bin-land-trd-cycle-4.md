## B1 — blocking
Claim: §3.7's step-5 return clause puts `branch_head` into `facts` wherever the local `<branch>` existed — not only where its check failed — and `build`'s `detail` rule then emits it on every path that gets past step 5, so `detail.branch_head` is established on FM-4 through FM-9 and on the success path; §6's cells for those six failure modes do not name it, and under D-O2's rule that a cell names exhaustively what is established there, each of those six cells asserts it is not.
Location: specs/bin-land-trd.md §3.7, "what a step returns", line 451; against §6's rule paragraph at lines 962–971 and its FM-4 through FM-9 rows at lines 983–988; §6's conflict rule at lines 973–975; §5.3's `branch_head` row at line 829 and its emitted-not-dropped paragraph at lines 843–852; §3.2 step 5 at lines 192–216; §5.4's AC-LAND-T03 at line 937.
Evidence: Inferred by reading at `2246d503`; no git behaviour is at issue, so nothing here was run. The chain is four stated rules with no gap between them. (i) §3.7 line 451: "step 5 returns `local_head`, and also `branch_head` where the local `<branch>` existed **and was the ref its second check ran against**". Per §3.2 step 5 line 198, the second check runs against `<branch>` whenever `<branch>` exists locally — "Where `<branch>` exists locally, `git merge-base --is-ancestor <branch> <base>`" — so the stated condition is satisfied by existence alone, on passing paths as much as failing ones. (ii) §3.7's own framing covers the passing case: "Each step of §3.2 returns either the facts it established or a stop", and a step that passes returns the facts it established. (iii) "The sequence accumulates `facts` across steps." (iv) §3.7's `build` clause, added this cycle by D-O1: "`detail` is populated from the same accumulated `facts` under §5.3's key table: each key that table names is emitted where `facts` carries it and absent where it does not." `branch_head` is a key that table names, and `facts` carries it, so it is emitted. §5.3's new paragraph confirms the direction rather than blocking it: "a key `facts` carries on a path this column does not name is **emitted** there, not dropped." **Ruling: contradiction, not wording ambiguity.** The tight reading — that "was the ref its second check ran against" means "was the ref the *failing* check ran against" — is unavailable, for two reasons. First, this document has a distinct and consistently used vocabulary for the failure condition and §3.7 does not use it: §3.2 step 5 line 213 says "where it was the second check that **failed**", and §6's FM-3 cell says "where the local `<branch>` was the **failing** check". A reader has no license to read "ran against" as "failed" when the document says "failed" three times elsewhere for the same condition. Second, the parallel construction in the same sentence is genuinely a state condition, not a failure condition: "step 6 returns `prior_branch` where HEAD was on some branch other than `<branch>` when it ran" — and `prior_branch` is emitted on the success path, as §5.3's own row states. The trailing gloss "which is the field §5.3 requires on that refusal" is the only pull the other way, and it names *a* path on which the field is required, not the only path on which the step returns it; §5.3 requires `prior_branch` on the success path too, and that requirement closes no set either. Note also that this is not confined to the six cells: §3.2 step 5 does not say whether the guard short-circuits, so where the *first* check fails while a local `<branch>` also exists, the second check may still have run — and FM-3's own qualifier, "where the local `<branch>` was the failing check", is wrong in that state by the same chain.
Consequence: Concretely, on FM-5 — a named path that does not exist, in a worktree where `<branch>` already exists locally and is at or behind the base, which is the ordinary J2 state after a J1 landing — an implementer building `land.py` and `Report.build` from §3.7 emits `detail.branch_head` with an observed SHA. A test author deriving FM-5's expected report from §6's cell, which D-O2's rule at line 965 tells them is exhaustive ("What a cell does not name is not established there"), asserts `branch_head` is not established there. The test fails against a correct implementation. Because this repository separates test authorship from implementation for the same unit of work, that divergence is the expected outcome rather than a risk — the two-agents-disagree class §3.7 exists to remove, in the section that claims to remove it, for the third cycle running. The second cost is to D-O2 itself: §6's conflict rule at line 973 says "Where a cell and those sections disagree, those sections are normative and the cell is wrong", so the document's own account is that six of the eleven cells rewritten this cycle are wrong — the column D-O2 was run to make correct to one rule is incorrect on the majority of its rows, and correct only if the reader stops at §6 and never reaches §3.7.
Fix: Two routes, and they are not equal. **Tighten §3.7** — one clause, so step 5 returns `branch_head` only where its second check failed, matching §3.2 step 5, §5.3's `branch_head` row, §6's FM-3 cell, and AC-LAND-T03's given, all four of which already scope it that way, and leaving the six cells as landed correct. **Or widen the six cells** to name `detail.branch_head` where a local `<branch>` existed, which additionally requires rewording §5.3's `branch_head` meaning ("before step 6 **would have** rewritten it" is false on the paths where step 6 did rewrite it) and resolving the short-circuit question in §3.2 step 5. I recommend the first: it is one clause against three edits, and the objection that it makes the tool discard an observed fact does not hold — D-O1's emitted-not-dropped rule governs what `build` does with facts it is handed, not which facts a step must establish, so a step that does not return `branch_head` on a passing path is not the report "declining to claim a fact", which is the thing D-O1 rules out. Either route is a TRD-level decision about the tool's own report contract, which §3.3's OQ-5 precedent makes this document's to take; neither touches the PRD.

Location: specs/bin-land-trd.md §5.3, lines 850–852 ("A reader may therefore not treat a key's absence from a path as a claim, and no test written to this document may assert one"); §6, line 965 ("What a cell does not name is not established there"); both added by `ff13c838` (*observed*, present in the diff's added lines and absent from `97888a8`).

So a `detail` key omitted from a cell is, per §6, a claim that it is not established, and per §5.3, not a claim at all and not assertable by any test. The drafting shows the tension was felt without being resolved: FM-4's cell states its one negative explicitly rather than by omission — "No `detail.prior_branch`: step 6 is the step that failed, so HEAD never moved" — which is the form §5.3 would permit, and no other cell does it.

The second cost is that B1's two fix routes read differently under the two rules — under §5.3 the extra `branch_head` is harmless surplus, under §6 it falsifies six cells — so a decision session disposing of B1 without disposing of this pair can reasonably conclude either that B1 is blocking or that it is nothing.
Fix: One sentence, in whichever of the two paragraphs is chosen as the subordinate. The natural reading is that §5.3's openness governs the *report* — a consumer may not branch on a key's absence — while §6's exhaustiveness governs the *document's account of the design* — a cell that omits a key is a drafting claim about what the design establishes, checkable by review against §3.2/§3.7, not by a test against the tool. Saying that distinguishes the two audiences and leaves both rules standing; saying nothing leaves them contradicting.
