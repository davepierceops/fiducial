## B1 — blocking
Claim: The divergence guard at §3.2 step 5 tests local `HEAD`, but step 6 resets the named branch, so when `HEAD` is on some other branch the guard passes and `checkout -B` orphans every unpushed commit on `<branch>` — falsifying §3.3's stated guarantee that no commit becomes unreachable.
Location: specs/bin-land-trd.md §3.2 steps 5 and 6; §3.3, the "HEAD moves" bullet.
Evidence: Verified by running, against `git` 2.55.0 in a throwaway repository. Setup: `main` at `a1c1fdf`, local branch `feature` carrying two commits `main` does not (tip `6f0aa61`), `HEAD` checked out on `main`, and a resolved base of `a1c1fdf`. Step 5's `git merge-base --is-ancestor HEAD <base>` exits 0, so the sequence continues. Step 6's `git checkout -B feature <base>` then reports "Switched to and reset branch 'feature'" and sets `feature` to `a1c1fdf`. `6f0aa61` is thereafter reachable from no ref (`git rev-list --all` does not contain it) and not reachable from `HEAD` (`git merge-base --is-ancestor 6f0aa61 HEAD` exits non-zero). §3.3 asserts the contrary: "The prior branch's ref is not touched and no commit becomes unreachable, because step 5 has already established that local HEAD is an ancestor of the base." That reasoning holds for the branch `HEAD` was on and says nothing about `<branch>` itself, which is the ref step 6 moves.
Consequence: A session whose `HEAD` is not on `<branch>` — the ordinary state after any checkout away from it, and the state §3.3's own "HEAD moves" bullet is written to cover — loses unpushed work on `<branch>` to the reflog with no diagnostic and a zero exit, because the loss happens before anything the tool checks. This is the destructive class PRD §7 puts under "Not accepted", reached through a path the design believes it has ruled out. §3.4 already identifies exactly this mechanism as the reason to refuse in the branch-absent arm — "proceeding in this state would move `<branch>` ... and abandon them to the reflog" — so the document contains the argument against its own step 6 and applies it to only one arm.
Fix: Extend the guard to the ref step 6 moves, not only to `HEAD`: where `<branch>` exists locally, require `git merge-base --is-ancestor <branch> <base>` as well, and refuse with the same FM-3 shape when it fails. Then correct §3.3's "HEAD moves" bullet, whose safety claim is currently stated as established rather than as conditional on a check that does not exist.
Related: B2, O2.

## B2 — blocking
Claim: `git checkout -B` does not reset a pre-populated index, so content staged before the invocation lands in the commit alongside the named paths — violating AC-LAND-02 — and §5.1's state table asserts the opposite.
Location: specs/bin-land-trd.md §5.1, the state table row "The index | Reset by step 6's checkout"; §3.2 steps 6, 7, 8; specs/bin-land.md §6 AC-LAND-02.
Evidence: Verified by running, against `git` 2.55.0 in a throwaway repository. With `unrelated.txt` staged before the invocation (`git status --short` reports `A  unrelated.txt`), `git checkout -B target <base>` reports "Switched to a new branch 'target'" and leaves the index unchanged — `git status --short` still reports `A  unrelated.txt`. Step 7's `git add -- wanted.txt` and step 8's `git commit` then produce a commit whose file list is `unrelated.txt` and `wanted.txt` (*observed*, `git show --name-only`). AC-LAND-02 reads "Given named files, only those paths appear in the resulting commit" (*observed*, PRD §6).
Consequence: An execution session that ran `git add` for any reason before invoking `bin/land` — a habit the tool exists to replace and which sessions will carry into the transition — silently lands unrelated content on the branch. The report's `files` list carries only the named paths, per §5.2, so the extra file appears in neither the per-file comparison nor the output: the tool would land content it does not report and exit 0. That is PRD §7's "Any output that reports a landing the tool did not observe" read from the other side, and it defeats AC-LAND-02 on a path no criterion currently induces.
Fix: Make step 7 authoritative over the index rather than additive — reset the index to the base before staging (`git reset --mixed <base>`, or `git read-tree <base>`, neither of which touches the working tree) — and correct §5.1's row, which currently states as established a behaviour git does not have. Whichever operation is chosen, §3.3's "what the working tree holds afterwards" paragraph needs the matching sentence, since it is the paragraph a reader consults for this.
Related: B1.

## B3 — blocking
Claim: §4.3 asserts that AC-LAND-06's comparison is the check that would catch the failure class `policies/remote-write-verification-policy.md` records, and the document's own argument two paragraphs later shows it would not — so the goal PRD §1 names as this tool's distinguishing purpose is not met by the design as specified.
Location: specs/bin-land-trd.md §4.3, both paragraphs; §9 OQ-6; specs/bin-land.md §1 (the `remote-write-verification-policy` bullet), §4 G5, §6 AC-LAND-06.
Evidence: Inferred by reading, with the underlying git property carried as the document's own *inferred* label and the policy text verified by running. §4.3 establishes that under git's content addressing a commit SHA determines its tree, so once `ls-remote` returns the pushed commit SHA the per-file blob SHAs necessarily agree. It then claims the check "is the one that would catch the failure class `policies/remote-write-verification-policy.md` records". That policy's Known gap describes "a write whose response is truthful and whose commit is real, because the *request* was wrong: a call carrying a placeholder string as its content parameter replaced a ~64KB file ... with 19 bytes" (*observed*, `policies/remote-write-verification-policy.md` lines 48-56). The git-transport analogue of a wrong request is a mis-staged file — and a mis-staged file is committed locally with the wrong content, so its blob SHA in the local commit and its blob SHA at the remote agree exactly. §4.3 says so itself: the stronger form "would additionally catch a mis-staged file". So the comparison AC-LAND-06 specifies catches the class only in a transport where commit-SHA equality does not already imply blob equality, which is not this tool's transport.
Consequence: PRD §1 states that closing that gap "is this tool's distinguishing goal", and G5 states "This goal is what closes the gap `policies/remote-write-verification-policy.md` names as open" (*observed*). Under the design as written, the released tool would carry a content-verification step that is arithmetically redundant with its landing check, and the gap would stay open while the PRD, the TRD, and every change package recorded it as closed. §4.3 currently reads as reassurance on this point — its first paragraph concedes the redundancy "for a git-transport write" and its second reclaims it — so a reader arrives at OQ-6 believing it is an optional strengthening rather than the question the goal depends on.
Fix: Correct §4.3's second sense: state that under git transport the per-file comparison adds nothing to the `ls-remote` check, and that the check which would catch the policy's class here is the stronger one — fetched bytes against the named file on disk. Then re-rank OQ-6 accordingly: it is not "whether the comparison should be stronger" but "whether G5's stated purpose is achieved by AC-LAND-06 as written". That reframing is what puts the amendment decision in front of Dave with its actual weight, and it is his to make because it changes an agreed criterion.
Related: B4.

## B4 — blocking
Claim: §5.2's value-domain rules for `prior_head` and `verification` contradict the null-on-unknown rule stated three lines above them, so the report format is self-inconsistent on every failure path and AC-LAND-T01 cannot be satisfied as written.
Location: specs/bin-land-trd.md §5.2, the "Rules the format holds on every path" list; §5.4 AC-LAND-T01; §6, the FM table, FM-1 row.
Evidence: Inferred by reading at this SHA. The list states, in order: "`value` is `null` wherever `class` is `"unknown"`"; then "`prior_head.value` is either a 40-character SHA or the literal string `"created"`"; then "`verification.value` is `"complete"` or `"incomplete"`". The rules are introduced as ones "the format holds on every path". §6's FM-1 row states that on a fetch failure "All five contract fields [are] `unknown` except `branch`", which by the first rule makes `prior_head.value` and `verification.value` null — a value neither of the two later rules admits. AC-LAND-T01 then asserts both properties simultaneously: keys exactly the six, and "every leaf whose `class` is `"unknown"` has `value` of `null`". The two readings produce different reports on all nine detected failure modes, and AC-LAND-T01, the criterion whose whole burden is "a failed landing is still machine-readable", cannot be written against a contract that contradicts itself on the failure paths.
Fix: Give the two rules the `files` rule's shape — "`prior_head.value` is a 40-character SHA, the literal string `"created"`, or `null`; `null` only with `class: "unknown"`", and the same for `verification.value` over `"complete"` / `"incomplete"`. No other section changes; §6's FM rows are already correct and are what the rules should have matched.

## N1 — non-blocking
Claim: §8's Performance constraint states "one `ls-remote` before the write", and §3.2 step 3 performs two of them in the branch-absent arm — which is J1, the first journey every session runs.
Location: specs/bin-land-trd.md §8, Performance; §3.2 step 3.
Evidence: Inferred by reading at this SHA. Step 3 reads `git ls-remote --heads origin <branch>` to answer presence, and then: "Where the branch is absent, the same read is performed for `main` and its SHA is the base." §8 asserts "one invocation performs exactly one `fetch` for objects, one `ls-remote` before the write, one `push`, and one `ls-remote` plus one targeted `fetch` after it." The enforcing test §8 describes asserts only "that `push` appears exactly once on the success path and at most once on every failure path", so the ls-remote count is stated but not enforced, and the discrepancy would not surface as a failing test.
Consequence: §8 is the section a Test Designer derives the negative performance constraint from, and the count it states is false on the branch-absent arm. A test written to §8 fails on J1; a reader auditing the tool's network operations against §8 finds one more than the document admits. The substantive property — exactly one write per invocation — is unaffected and is the part the described test actually covers.
Fix: State the count per arm — "one `ls-remote` before the write, or two where the branch is absent and `main` must be read" — or collapse step 3 to a single `git ls-remote --heads origin <branch> main`, which answers both in one round trip and makes §8's sentence true as written.

## N2 — non-blocking
Claim: AC-LAND-T01's enumeration is wrong in both directions — it includes FM-10, which by §6's own row emits nothing, and excludes the usage-error path, which §3.2 step 11 requires it to cover.
Location: specs/bin-land-trd.md §5.4 AC-LAND-T01; §3.2 steps 1 and 11; §6, FM-10 row; §7, exit-code table.
Evidence: Inferred by reading at this SHA. Step 11 states "The report is serialized to stdout on every terminal path, including every failure path." AC-LAND-T01 scopes itself to "each terminal state of §3.2 — the success path and each failure mode enumerated in §6". §6's FM-10 row reads "The invocation is killed mid-sequence | Not detected by the tool | — | Nothing is emitted", so it is inside T01's enumeration and cannot satisfy T01. In the other direction, §7 maps exit 2 to "Usage error", §3.2 step 1 places parsing in `bin/land` via `argparse` (§1, §3.1), and §6 enumerates no usage failure mode — so a usage error is a terminal path that step 11's rule reaches, T01's enumeration does not, and the stated design cannot serve, since `argparse` exits before the sequence begins.
Consequence: A Test Designer writing AC-LAND-T01 has to silently drop one enumerated case and silently decide another, and both decisions change what the criterion proves. If usage errors emit no report, step 11's "every terminal path" is false and the report contract has an undocumented hole at the most common operator error; if they do, `bin/land` needs to intercept `argparse`'s exit, which is a design point §3.1's "Argument parsing, exit code, and nothing else of substance" does not anticipate.

## N3 — non-blocking

## N4 — non-blocking
Claim: `files` has no representation for *unknown*, so §6's failure rows asserting that the contract fields are `unknown` are unsatisfiable for it, and an empty list means two different things.
Location: specs/bin-land-trd.md §5.2, the `files` rule and the shape example; §6, FM-1 through FM-6 rows.
Evidence: Inferred by reading at this SHA. §5.2 makes `files` a list of per-entry objects, each carrying its own `class`; unknown-ness is expressible per entry and nowhere else. FM-1 states "All five contract fields `unknown` except `branch`", and `files` is one of the five (PRD G6). With no commit made — FM-1 through FM-6 — there are no entries, so the only available value is `[]`. FM-5 is "Nothing to commit ... or the staged set is empty", where `[]` is the true and established answer.
Consequence: `"files": []` asserts "this commit contained no files" on six failure modes where the tool established nothing of the kind, which is the observed/unknown collapse PRD G6 and AC-LAND-09 exist to prevent. A machine reader can recover the distinction from `detail.stage`, which is why this is non-blocking rather than blocking — but N3 records that `detail.stage`'s value set is itself unspecified, so the recovery path is currently no firmer than the thing it repairs.
Fix: Either give `files` a leaf form for the unestablished case — an object with `class: "unknown"` and `value: null` in place of the list, at the cost of a union type in the parse contract — or state in §5.2 that `files` is `[]` whenever no commit was made, that this is not a claim about the commit's contents, and that `detail.stage` is what distinguishes it from FM-5. The second is lighter and is probably what §6 already intends; it is not currently written anywhere.
Related: B4, N3.
