## F-1 — non-blocking
Claim: The revised fence-only sentence bounds containment of the colon-terminated literal, which is not the property the design rests on, and the permission it adds licenses a line that breaks that property.
Location: skills/directive-invariants.md:41–43, against :207–210
Evidence: Verified by running. Cycle 2's F-2 asked that line 40 say which string the rule bounds; the revision names the emitted literal by reference and adds "the bare token may appear in prose". Both halves are true of the file as committed: `mdmask.eligible` over the file returns no eligible line containing `WORKING-TREE DISPOSITION` followed immediately by a colon, and the bare token's one eligible occurrence is at :208, inside an inline code span in the match rule's own prose. But the property TRD §3.2 states as condition 2 — asserted by `test_q10_the_invariants_document_shows_the_label_only_inside_fences` and `test_b1_the_real_invariants_document_shows_the_label_only_inside_fences`, both read — is tested by `unfenced_labelled_statements`, which applies the *match rule*: leading content after stripping begins with the bare token, and a colon appears anywhere later on the line. The two bounds are not the same, and the difference is demonstrable. Running the helper over the file as committed returns `[]`. Running it over the same file with one unfenced prose line added — `WORKING-TREE DISPOSITION (exclusive assignment): an example an editor might write in prose.` — returns a hit at line 41, while `mdmask.eligible` over that same mutated file still returns no eligible line containing the colon-terminated literal. The added line satisfies the sentence at :41–43 exactly as written, carries the bare token in prose exactly as the sentence permits, and fails condition 2.
Consequence: This sentence is the file's own statement of the one property of the one file that makes G3 hold, and it is addressed to the editor who is bound by it. An editor who writes a worked example, a quoted disposition, or an illustrative labelled line into the preamble or into any of the four lint sections — the plausible case, since the document's whole purpose is to show authors both admitted forms — reads the sentence as permitting it, because the bare token is what such a line carries. The failure is loud rather than silent: two tests go red on a document the editor was told they had not broken, and they must then decide, with the document's own sentence on one side and the suite on the other, which is right. That is the same fork cycle 2's F-2 described, reached by a different route. The document already states the correct bound 165 lines further down, in the match rule at :207–210, and the sentence at :41–43 does not connect to it.
Fix: Bound the property by the match rule rather than by the literal — say that no eligible line of this document is a labelled disposition statement as the match rule below defines one, and that the bare token may otherwise appear in prose. That states the property the tests assert, keeps the emitted literal out of unfenced prose as the amendment requires, and needs no new fence. Criterion 12.

## F-2 — non-blocking
Claim: The invariant report format requires a worktree-removal status from every directive, including one whose disposition is the sole-tree form the same document admits.
Location: skills/directive-invariants.md:157, against :97 and :244–246
Evidence: Verified by reading, against the TRD's two region tables. `§Report format`'s body at :153–157 is a five-item list, unconditional, ending "- the worktree-removal status". The TRD's general-mode table emits it as region 12 and its cycle-mode table as row 14, so every generated skeleton in either mode carries it. The same document's `§Working-tree disposition prompt` fence at :92–98 works two admitted forms, the second being "This session works in the sole tree at the clone root.", and the revision's F-3 fix at :244–246 makes that form's membership test explicit — so the sole-tree form is not vestigial, it is the form the revision just finished making usable. Under it no worktree is created and none can be removed. The contrast is inside the document: `§Verification steps` at :137 states the rule for a step that did not happen — "A step you did not run is reported as not run, never as passed" — and `§Report format` states nothing for an item that cannot apply.
Consequence: An executor carrying a sole-tree directive reaches a required report item with no referent. It has three moves and the bundle picks none: report a line about a worktree that never existed, silently drop a required item from the report format the directive emitted verbatim, or stop and surface. Each is the executor deciding what the report format means, and the third costs an invocation. TRD §3.2 records that the sole-tree form has zero instances in the 144-file corpus and that the prompt's fence exists precisely so an author has that form to imitate; the first author to take it up hands their executor a report item the author never wrote and cannot see is wrong.
Fix: Condition the item on the disposition — the worktree-removal status, or that the directive assigned no worktree — so the item is answerable under either admitted form. One clause inside the existing list item; no section, fence, or marker line moves. Criterion 11.
