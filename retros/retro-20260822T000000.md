## Interpretation
- (1) A kickoff baton is a plan from the previous session, not a decision for this one. CoS should read it as state and still take the first message from Dave as the authority on scope — the predictable artifact to pre-stage is the one Dave's *current* intent implies, and when the kickoff is a bare line, one sentence confirming the scope costs less than a full wrong directive.
- (3) Vocabulary from a retired document leaks into its replacement. When retiring machinery, sweep the new text for the old nouns.
- (4) Memory of tooling is not evidence of tooling. The directive should have told the executor to run `bin/bundle --help` and report, not asserted flags. The executor's refusal to improvise is the methodology working; the defect was upstream.
- (6, 7) "Delivered like a directive" was read as "lands in the repo like a directive." What Dave means by the directive pattern is the *delivery surface*: one block, copy, paste. The repo-commit half is the execution session's job, and a baton has no execution session. The record now says so (baton text, Pass 2 item, and memory edit).

## Durable insights
- Baton = one paste block in chat, pasted as the next session's first message. No file, no executor. Every time.
- Before any directive cites a bin/ flag or interface, the directive instructs the executor to verify it with --help rather than assuming it; or CoS reads the script first.
- When a baton hands over scope, the first response still confirms scope against Dave's current intent before drafting a directive of any size.

## Candidate methodology changes
- Core or Decision Layer: state baton delivery as above; strike "committed to docs/batons/".
- Decision Layer, directive-writing: "Do not assert a bin/ flag from memory; instruct the executor to run --help and report."
- Retire the docs/batons/ directory once the rule lands, or keep it as history only.
