## Interpretation

- (1) Executor reports that live only in a prior chat are unrecoverable in
  practice. Reading source text from main was slower but produced observed
  claims rather than told ones, and every ruling cited what it rested on.
  The rulings held up at the gate: zero blocking findings.
- (2, 8) Two warning labels were being spent on nothing — "landmine" on routine
  behaviour, and irreversibility language on reversible operations. The cost is
  the same in both: the reader learns to skip the warning, which is the one
  outcome a warning must not produce.
- (3) The stop-on-intent wording plus an explicit "do not retry with different
  flags" line is the first pair that has produced a correct stop on a real
  failure. Two executors, same failure, opposite behaviour; the only variable
  was the directive text.
- (4, 5) Three of the session's four authoring errors were expectation lines
  written from a sandbox that differs from Dave's machine, or from memory of a
  count rather than a fresh measurement. Expectations the executor will check
  against are claims; they need the same read-before-assert discipline as any
  other claim. The executors' handling — flag, match against stop conditions,
  proceed — was exactly right, and the Reviewer gate's decision to file them
  against the directive rather than the change was the correct attribution.
- (6) A 67 KB full-file connector write was the wrong tool even before the
  timeout: it routes the entire tracker through the CoS's output, where a
  transcription error would be caught only by a stats guard. Executor-run
  directives carrying the delta verbatim are both safer and cheaper.
- (7, 9) Dave's pushbacks all landed on premises the CoS had stated from
  recall. Each was corrected by reading the file. The session's best decisions
  (retire-now-format-later, delete-not-rewrite) came after a read surfaced a
  fork the CoS had not anticipated; the worst proposals came before one.

## Durable insights

- **Read the inputs before drafting the directive, not after.** Two of the
  session's forks (PRD-not-committed, format mismatch) only existed because the
  decision log was read before the block was written. The directive-tooling
  gap this repo already names — directives are ungated — makes this the only
  gate a directive gets.
- **Expected-output lines are claims.** State only what was observed in the
  same environment, or say what to look for without a number.
- **A label that fires on routine events is worse than no label.** Reserve
  "landmine" for consequences Dave would act on; reserve irreversibility
  language for operations that are.
- **Directive text is the executor's behaviour.** Stop-on-intent plus
  do-not-retry produced a correct stop; the prior wording did not. Carry both
  lines by default.
- **Adapters are per-repo by nature; the portable thing is the corpus.** A
  file that looks portable and isn't is worse than none. How adopting projects
  reach fiducial is a design question for the PRD, not an adapter to write.

## Candidate methodology changes

- `docs/global-context/decision-layer.md` rule 3: add a test for what counts as
  a landmine — a consequence Dave would act on differently, or be surprised by,
  if unnamed; expected tool behaviour and tracked open items are not.
- `skills/command-blocks.md`, the expected-output criterion: the stated
  expectation must be observed in the same environment the block will run in,
  or be qualitative. A count measured in a different sandbox is not an
  expectation.
- `skills/directive-authoring.md`: two default lines for every working-tree
  disposition — "If the add fails for any reason, stop and report; do not retry
  with different flags" and the intent-based mutation stop — pending the
  executor STOP wording change already queued.
- `skills/directive-authoring.md`: an expectations rule — every count or file
  set the directive states as "expected" is measured by the author against the
  reviewed ref before dispatch, with the sweep scope stated (whole tree, not
  governed paths).
- Source-of-truth or adapter guidance: an adapter restates no rule, and
  fiducial itself carries no adapter for adopting projects until the
  bundle-system PRD decides how a project reaches the corpus.
